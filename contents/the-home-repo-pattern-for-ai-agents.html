The Home Repo Pattern for AI Agents

This post was written by an LLM (Claude) and edited by me.

Most companies split their code across many repos: a storefront, a payments API, an admin dashboard, and twenty more you touch now and then. 

acme-storefront/
acme-payments-api/
acme-admin-dashboard/
...20 more

An AI coding agent works better with context: rules (CLAUDE.md or AGENTS.md), skills, and notes about the project. That context has to live somewhere.

“Where do the agent's rules and skills live when the code is spread over thirty repos?”

Two bad answers

Copy them into every repo. Now you have thirty copies. You fix a skill in one repo and the other twenty-nine drift.

Put them in your user folder (~/.claude). Every repo can see them, but your teammates can't. They aren't versioned, and they fall behind. That folder is also meant for your preferences, not the team's rules.

The fix: a home repo

Make one extra repo whose only job is to be the agent's home. You always start the agent there, and it reaches the other repos by file path. 

        ┌────────────────────────────┐
        │         HOME REPO          │  ← start the agent here
        │  CLAUDE.md  (map + rules)  │
        │  .claude/skills/           │
        │  wiki/      (facts)        │
        │  tools/                    │
        └──────┬─────────┬─────────┬─┘
               │ path    │ path    │ path
               ▼         ▼         ▼
         storefront  payments  dashboard
         (own PRs)   (own PRs) (own PRs)
“How does the agent know where the other repos are?”

You tell it. The home repo's CLAUDE.md holds a map, like a phone book: 

## Repos

| Repo         | Path                      | What               |
|--------------|---------------------------|--------------------|
| Storefront   | ~/code/acme-storefront    | Customer web app   |
| Payments API | ~/code/acme-payments-api  | Payment service    |
| Dashboard    | ~/code/acme-admin         | Internal admin UI  |

Working in a repo:
1. Read its own CLAUDE.md first.
2. Missing on disk? Clone it.
3. Commits and PRs go to that repo, not this one.

That is the whole trick. The agent starts at home, so it loads every rule and skill. When a task touches the storefront, it opens that path, works there, and opens its pull request there.

What you get

  • One source of truth. Fix a skill once and every session has the fix.
  • Versioned. It's a normal git repo, so changes get reviewed and shared.
  • Cross-repo work in one session. One request becomes a fix in the storefront, a matching change in the payments API, and two pull requests.
  • Team settings. A committed .claude/settings.json gives everyone the same agent setup.
  • Room to grow. A wiki of project facts and custom tools (Slack, Jira, email) fit naturally in the same place.
“What happens when you have four hundred repos, not twenty?”

Scaling with progressive disclosure

A flat list works for twenty to forty repos. Past that, group the repos and let the agent drill down, reading only the file it needs: 

CLAUDE.md
  ├── repos/frontend.md  → storefront, dashboard, ...
  ├── repos/backend.md   → payments-api, orders-api, ...
  └── repos/internal.md  → tooling, scripts, ...

When not to bother

If all your code can live in one monorepo, use the monorepo. The home repo is for when it can't, for example because some repos must be public and others private, or because nobody will agree to merge them.

Takeaway

Context lives in one place. Code lives where it belongs. The agent always starts at home.
