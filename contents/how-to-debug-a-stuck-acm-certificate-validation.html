How to Debug a Stuck ACM Certificate Validation

You request an AWS Certificate Manager (ACM) certificate for two domains. One turns green. The other sits at Pending validation, and there is no button to make it try again. 

Domain            Status
example.com       Pending validation
example.com.au    Success
“The record is there. Why won't it verify?”

The AWS console only shows you the result. To find the cause, you have to look at DNS the way ACM does: from the public internet. This article does that with three command-line tools and two free Google services:

  1. AWS CLI → what ACM expects to find
  2. dig / nslookup → what DNS actually says
  3. curl + Google's dns.google API → the same lookup, as JSON, from any machine
  4. Google Public DNS (8.8.8.8) → an outside resolver that ignores your laptop's cache
  5. Google Admin Toolbox Dig → a browser version, when you can't install anything

How DNS Validation Works

For every domain on the certificate, ACM gives you one CNAME record:

Name:  _a1b2c3d4e5f6.example.com.
Value: _f6e5d4c3b2a1.abcdefghij.acm-validations.aws.

You publish it in the domain's DNS. Then ACM, on its own schedule, looks up the name from the internet. If the answer matches the value exactly, the domain flips to Success.

Two rules matter:

  • A domain that hasn't validated after 72 hours fails, and you have to request the certificate again.
  • Within one AWS account, ACM normally gives the same CNAME to the same domain every time. Remember this one. It's the way out at the end.
“So if it's stuck, one of those lookups must be failing. Which one?”

Work through the five checks below in order. Each one rules out one cause.

Check 1: What Does ACM Expect?

Don't copy the value off the console table. It's truncated, and it's easy to grab the wrong row. Ask the CLI:

aws acm list-certificates --region us-east-1

aws acm describe-certificate \
  --region us-east-1 \
  --certificate-arn arn:aws:acm:us-east-1:111122223333:certificate/abcd-1234 \
  --query "Certificate.DomainValidationOptions[].{domain:DomainName,status:ValidationStatus,name:ResourceRecord.Name,value:ResourceRecord.Value}" \
  --output json

You get the exact name and value for each domain, along with its status:

[
  {
    "domain": "example.com",
    "status": "PENDING_VALIDATION",
    "name": "_a1b2c3d4e5f6.example.com.",
    "value": "_f6e5d4c3b2a1.abcdefghij.acm-validations.aws."
  },
  {
    "domain": "example.com.au",
    "status": "SUCCESS",
    "name": "_0f9e8d7c6b5a.example.com.au.",
    "value": "_5a6b7c8d9e0f.abcdefghij.acm-validations.aws."
  }
]

Keep this terminal open. Every check below compares DNS against these two strings.

Use the right region. A certificate for CloudFront always lives in us-east-1. One for a load balancer lives in the load balancer's region.

Check 2: Who Answers for the Domain?

A record only counts if it's in the zone the internet actually uses. Ask Google Public DNS which nameservers are in charge of the domain: 

dig NS example.com @8.8.8.8 +short

# Windows
nslookup -type=NS example.com 8.8.8.8
ns-187.awsdns-23.com.
ns-991.awsdns-59.net.
ns-1131.awsdns-13.org.
ns-1754.awsdns-27.co.uk.

Now compare with the hosted zone you put the record in:

aws route53 list-hosted-zones-by-name --dns-name example.com

aws route53 get-hosted-zone --id Z0123456789ABC \
  --query "DelegationSet.NameServers"
“They're different. Does that matter?”

It's the whole problem. The registrar points the world at one set of nameservers, and your record sits in a zone nobody asks. This happens when a hosted zone is deleted and created again (each new zone gets new nameservers), or when the domain is registered somewhere else, such as GoDaddy, and its DNS is still managed there.

The fix: create the record in the zone the registrar actually points to, or update the registrar's nameserver list to match the Route 53 zone.

Check 3: Can the Internet See the Record?

Look up the validation name through Google Public DNS:

dig CNAME _a1b2c3d4e5f6.example.com @8.8.8.8 +short

# Windows
nslookup -type=CNAME _a1b2c3d4e5f6.example.com 8.8.8.8

No dig? No problem. Google runs a DNS-over-HTTPS API that returns JSON, so plain curl works on any machine, including a CI runner: 

curl -s "https://dns.google/resolve?name=_a1b2c3d4e5f6.example.com&type=CNAME"
{
  "Status": 0,
  "Answer": [
    {
      "name": "_a1b2c3d4e5f6.example.com.",
      "type": 5,
      "TTL": 300,
      "data": "_f6e5d4c3b2a1.abcdefghij.acm-validations.aws."
    }
  ]
}

How to read it:

  • "Status": 0 + an Answer → the record is public. Go to check 4.
  • "Status": 3 (NXDOMAIN) → the name doesn't exist. Go back to check 2.
  • "Status": 0 but no Answer → the name exists but has no CNAME, often because a TXT or A record was created instead.

If you'd rather click than type, the same lookup is at Google Admin Toolbox Dig. Pick CNAME and paste the name.

“I created it ten minutes ago and Google says NXDOMAIN. Is it broken?”

Maybe not. A resolver caches a “doesn't exist” answer too, for as long as the zone's SOA record says. Skip all caches by asking one of the domain's own nameservers from check 2 directly: 

dig CNAME _a1b2c3d4e5f6.example.com @ns-187.awsdns-23.com +short

If the domain's own nameserver has the record but Google doesn't, it's a cache. Wait out the TTL. If the nameserver doesn't have it either, the record isn't in that zone.

Check 4: Is It the Right Value?

Put the DNS answer from check 3 next to the value from check 1. They must match character for character, including the trailing dot.

The usual ways they go wrong:

  • Doubled domain. Many DNS providers add the domain to whatever you type in the name box. Paste _a1b2c3d4e5f6.example.com and you get _a1b2c3d4e5f6.example.com.example.com. Type only _a1b2c3d4e5f6.
  • Old record. A CNAME left over from a certificate in another AWS account. It has the right name but the wrong value.
  • Wrong row. The value for example.com.au pasted under example.com.

Spot the doubled domain with a single query:

curl -s "https://dns.google/resolve?name=_a1b2c3d4e5f6.example.com.example.com&type=CNAME"

If that one answers, you've found it.

Check 5: Is a CAA Record Blocking Amazon?

A CAA record lists the certificate authorities that may issue certificates for a domain. If one exists and Amazon isn't on the list, ACM refuses, even with perfect validation records. 

dig CAA example.com @8.8.8.8 +short

# Works everywhere, including Windows, where nslookup can't query CAA
curl -s "https://dns.google/resolve?name=example.com&type=CAA"
  • No Answer → no CAA record. Any CA may issue. Fine.
  • An answer without amazon.com (or amazontrust.com) → add 0 issue "amazon.com".

CAA is checked at the domain and then at each parent. For app.example.com, check example.com too.

All Five Pass. Now What?

Then nothing is wrong. ACM just hasn't looked again yet. It re-checks pending domains on its own schedule: usually within about 30 minutes, sometimes a few hours.

“Can I force it to check now?”

No. There's no re-validate button, CLI command or API call. But remember rule two from the start: within one account, a domain gets the same CNAME every time. So request a fresh certificate for the same domains: 

aws acm request-certificate \
  --region us-east-1 \
  --domain-name example.com \
  --subject-alternative-names example.com.au \
  --validation-method DNS

Confirm that it asks for the record you already have:

aws acm describe-certificate --region us-east-1 \
  --certificate-arn <NEW_ARN> \
  --query "Certificate.DomainValidationOptions[].ResourceRecord"

A new request is checked right away, and the record is already there, so it's usually issued within minutes. Let the CLI wait for you: 

aws acm wait certificate-validated --region us-east-1 --certificate-arn <NEW_ARN>

Then point CloudFront, the load balancer or API Gateway at the new ARN, and delete the old pending certificate.

If check 4 found a wrong value, a new certificate won't help. Fix the record instead, and the old certificate validates on ACM's next check.

The Whole Thing as One Script

This runs checks 1, 3, 4 and 5 for every domain on a certificate. It only needs the AWS CLI, curl and jq, so it also runs in a CI job. 

#!/usr/bin/env bash
# Usage: ./check-acm.sh <certificate-arn> [region]
set -euo pipefail

ARN="$1"
REGION="${2:-us-east-1}"

aws acm describe-certificate --region "$REGION" --certificate-arn "$ARN" \
  --query "Certificate.DomainValidationOptions[]" --output json |
jq -c '.[]' | while read -r row; do
  domain=$(jq -r '.DomainName' <<< "$row")
  status=$(jq -r '.ValidationStatus' <<< "$row")
  name=$(jq -r '.ResourceRecord.Name' <<< "$row")
  want=$(jq -r '.ResourceRecord.Value' <<< "$row")

  # What Google Public DNS sees
  got=$(curl -s "https://dns.google/resolve?name=${name}&type=CNAME" |
        jq -r '.Answer[0].data // "NONE"')

  # Any CAA record on the domain
  caa=$(curl -s "https://dns.google/resolve?name=${domain}&type=CAA" |
        jq -r '[.Answer[]?.data] | join(", ") | if . == "" then "none" else . end')

  if [[ "$got" == "$want" ]]; then match="yes"; else match="NO"; fi

  echo "$domain"
  echo "  ACM status : $status"
  echo "  expected   : $want"
  echo "  public DNS : $got"
  echo "  match      : $match"
  echo "  CAA        : $caa"
done

Simple Real-Life Analogy

Think of ACM as a courier who has to find a note pinned to your front door.

  • Check 1 → read the courier's instructions so you know what the note must say.
  • Check 2 → make sure you pinned it to the house the map points to, not your old flat.
  • Check 3 → walk out to the street and look at the door yourself.
  • Check 4 → read the note. Is it the right one, spelled correctly?
  • Check 5 → is there a “no couriers except FedEx” sign on the gate?
  • New request → book another delivery. The note is already up, so this courier finds it at once.

Summary

  • Get the exact expected name and value from aws acm describe-certificate, not the console table.
  • Check the domain's real nameservers with dig NS @8.8.8.8 and compare them with your hosted zone.
  • Look the record up through 8.8.8.8 or https://dns.google/resolve, then ask the domain's own nameserver to skip caches.
  • Match the value character for character, and watch for a doubled domain in the name.
  • Check CAA. Windows nslookup can't, but dns.google can.
  • If everything checks out, ACM just hasn't looked yet. Wait, or request a new certificate, which reuses the same record.
