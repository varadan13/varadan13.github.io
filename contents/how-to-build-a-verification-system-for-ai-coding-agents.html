How to Build a Verification System for AI Coding Agents

An AI agent writes a feature. The build is green, the agent says "done", and the pull request looks fine. None of that tells you the feature works. A green build only proves the code compiled and the tests that exist passed. It says nothing about the requirements nobody wrote a test for.

“How do I know the agent built what I asked for, and not just something that compiles?”

This article is a plan for answering that question with evidence. It covers what to read first, the three separate things you need to verify, a worked point-of-sale (POS) example, and a score model that keeps "unproven" from passing as "done".

2. Three Different Questions

"Verify the AI's work" is really three separate problems. Mixing them up is how a well-behaved agent ships a broken refund flow, or how a working feature hides a tangled design.

  • Agent evaluation: did the agent follow the right process and produce good code? You check its trace: what it read, what it ran, what it changed.
  • Application verification: does the software meet the user's requirements? You run the app and test its behaviour.
  • Architecture verification: does the code respect the intended structure? You check imports, dependencies and where the logic lives.
“Can't I just average the three into one quality score?”

No. An agent that followed every rule can still ship a wrong tax calculation, and correct code can still break every layering rule you have. One number hides which problem you have. Keep three scores, each with its own evidence.

3. Write Requirements the Machine Can Check

Everything starts from the specification. A sentence like "refunds should be handled correctly" can't be verified. Split each requirement into a given / when / then with an ID, a priority and the checks that prove it: 

# spec/refunds.yaml
- id: R3
  title: A refund cannot exceed the amount paid
  priority: critical
  given: an order paid in full for 100.00
  when: a refund of 120.00 is requested
  then:
    - the API rejects it with 422
    - no refund row is written
    - the order balance is unchanged
  verified_by:
    - type: api
      test: TestR3_RefundCannotExceedAmountPaid
    - type: db
      check: refunds table has no row for the order

The verified_by list matters most. It links each requirement to the tests that prove it. A requirement with an empty list isn't failing. It's not verified, and the report must say so.

The matching test, in Go, names the requirement it covers:

func TestR3_RefundCannotExceedAmountPaid(t *testing.T) {
	order := createPaidOrder(t, 100_00) // amounts in cents

	resp := requestRefund(t, order.ID, 120_00)

	if resp.StatusCode != http.StatusUnprocessableEntity {
		t.Fatalf("want 422, got %d", resp.StatusCode)
	}
	if n := countRefunds(t, order.ID); n != 0 {
		t.Fatalf("want 0 refund rows, got %d", n)
	}
}
“Why check the database as well as the HTTP status?”

A handler can return 422 after it has already written the refund. The status code is what the API says. The row count is what actually happened. Run the database in a throwaway container (Testcontainers) so each run starts from a known state.

4. A Concrete POS Example

Say you asked an agent to build the order and payment core of a POS. The spec has seven requirements: 

ID  Requirement                                     Priority  Weight
R1  Total = sum(qty x price) - discounts + tax      critical  3
R2  Percentage discount is applied before tax       critical  3
R3  A refund cannot exceed the amount paid          critical  3
R4  Split card + cash settles only at exact total   major     2
R5  Tax rounds half-up to 2 places per order        major     2
R6  Receipt shows a discount line                   minor     1
R7  A voided item disappears from the kitchen       major     2
    ticket

Each one is checked a different way:

  • R1, R2, R5: Go API tests with fixed baskets, for example 3 items, a 10% discount and 8.25% tax, with the expected total worked out by hand.
  • R3, R4: API tests plus database checks, as shown above.
  • R6: a Playwright test that completes a sale, screenshots the receipt and asks a model whether a discount line is visible.
  • R7: nothing yet. The agent built the feature but wrote no test for it.

The run comes back like this:

R1  PASS          api test
R2  PASS          api test
R3  FAIL          refund of 120.00 on a 100.00 order returned 200
R4  PASS          api test + db check
R5  PASS          api test
R6  PASS          screenshot, AI-judged
R7  NOT VERIFIED  no test linked

The agent reported "all tests pass", and it was right: every test that existed passed. But no test covered R3's limit, and none covered R7. The verification run found the real refund bug only because the spec required a test for R3.

5. The Score Model

Each requirement gets three values:

  • Weight (w): critical = 3, major = 2, minor = 1.
  • Status (s): PASS = 1, FAIL = 0, NOT VERIFIED = 0.
  • Evidence confidence (c): a deterministic test (API, database or browser assertion) = 1.0. An AI-judged check, such as a screenshot read by a model, = 0.6. No evidence = 0.

From those, the application side gets two numbers:

correctness = sum(w * s * c) / sum(w)
coverage    = sum(w for every requirement that has a result) / sum(w)
“Why does NOT VERIFIED score 0 instead of being left out?”

If you leave it out, a project with one passing test and fifty untested requirements scores 100%. Counting it as 0 means unproven work pulls the score down. Coverage then tells you how much of the gap is missing evidence rather than broken code.

The POS run, scored

         w   s   c    w*s*c
R1       3   1   1.0  3.0
R2       3   1   1.0  3.0
R3       3   0   1.0  0.0
R4       2   1   1.0  2.0
R5       2   1   1.0  2.0
R6       1   1   0.6  0.6
R7       2   0   0    0.0
total   16            10.6

correctness = 10.6 / 16 = 66%
coverage    = 14 / 16   = 88%

Gates beat averages

A score is for trends. A release decision needs hard rules on top of it:

  • Any critical requirement that FAILs blocks the release.
  • Every critical requirement must have deterministic evidence (c = 1.0). A model's opinion of a screenshot isn't enough for money.
  • Correctness and coverage must not drop below the last release.

The POS run is BLOCKED by R3, whatever the 66% says.

The other two scores

Agent score comes from the trace: a checklist of process checks, each pass or fail. For the POS run: 

read the spec before editing code       PASS
ran the full test suite before "done"   PASS
stayed inside the allowed directories   PASS
final claim matches the evidence        PASS
did not edit existing tests or spec     FAIL  changed an expected total in a test

agent score = 4 / 5 = 80%   (hard fail: edited a test to make it pass)

Editing a test to make it pass is a hard fail, just like a critical requirement failing. Flag it however high the rest of the score is.

Architecture score comes from dependency and placement rules, checked by static analysis: 

domain/ imports nothing from http/ or db/       PASS
payments go through the PaymentGateway interface PASS
no import cycles                                 PASS
pricing and refund rules live in domain/          FAIL  refund limit computed in handlers/refund.go

architecture score = 3 / 4 = 75%

The architecture failure and the R3 bug have the same cause. The refund check was written in the HTTP handler instead of the domain layer, and one route skipped it. That's why the three scores are kept apart: each points at a different fix.

6. The Report

Write the report as JSON, so CI can read the gates, and render the same data as HTML for people. One entry per requirement, each pointing to its evidence: 

{
  "run": "2026-11-05T10:42:00Z",
  "verdict": "BLOCKED",
  "blocked_by": ["R3"],
  "scores": {
    "application": { "correctness": 0.66, "coverage": 0.88 },
    "agent": { "score": 0.80, "hard_fails": ["edited-test"] },
    "architecture": { "score": 0.75 }
  },
  "requirements": [
    {
      "id": "R3",
      "status": "FAIL",
      "confidence": 1.0,
      "evidence": [
        "logs/R3-api.txt",
        "db/R3-refunds-snapshot.json"
      ]
    },
    {
      "id": "R7",
      "status": "NOT VERIFIED",
      "confidence": 0,
      "evidence": []
    }
  ]
}

7. What to Build: specguard

The project is a standalone verification tool, working name specguard. The planned stack:

  • Orchestration: Go.
  • Spec format: YAML or JSON.
  • Agent communication: MCP.
  • LLM calls: Vercel AI SDK or the model APIs directly.
  • Browser checks: Playwright.
  • API checks: Go tests.
  • Database checks: Testcontainers.
  • Visual checks: Playwright screenshots judged by a model.
  • Reports: JSON and HTML.

First milestone

  1. Take a project requirements document.
  2. Turn it into structured acceptance criteria, like the YAML above.
  3. Generate tests, or link existing ones, for each criterion.
  4. Run them against the application.
  5. Capture screenshots, logs and results.
  6. Produce a per-requirement PASS / FAIL / NOT VERIFIED report.
“If an LLM writes the tests in step 3, who checks the tests?”

A person, at least at first. A generated test is a claim about the spec, so review it against the spec, not against the code. Mutation testing helps too: change the code on purpose, for example flip the refund comparison, and check that some test fails. If nothing fails, the test isn't really checking anything.

Summary

  • The specification defines what should exist.
  • The implementation defines what was built.
  • The tests establish what actually works.
  • The evidence establishes why you believe it works.
  • The auditor identifies what remains unproven.

Keep agent, application and architecture scores separate. Count NOT VERIFIED as 0. Let critical failures block a release whatever the average says. The goal is CI/CD for correctness, not just CI/CD for builds that pass.
