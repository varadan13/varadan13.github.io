How to Build a Widget Library as Part of a Static Site Deploy

You have a plain static site: a pages/ folder of HTML that a small Node script copies to dist/, and CI syncs to a bucket. No framework. Next to it sits a widget library, a Vite project that compiles a few Web Components into one file, pages/assets/widgets.js.

Until now someone built that file by hand and committed it. You want the deploy to build it instead, and you want it to know which API it talks to.

“How do I make one build compile both, and give the widgets the right API key for each environment?”

Here it is, in four steps.

1. See What the Build Does Today

Start with the root package.json:

"scripts": {
  "build:DEV1": "node scripts/build.mjs dev",
  "build:PROD": "node scripts/build.mjs prod"
}

The script copies pages/ to dist/ unchanged and adds only what depends on the environment: a robots meta tag on each page, robots.txt, and sitemaps for prod. CI runs npm run build:$ENVIRONMENT, then syncs dist/.

The widget library is a separate project with its own package.json. Its Vite config writes straight into the site's assets folder: 

// widget-library/vite.config.ts
build: {
  outDir: resolve(import.meta.dirname, "../pages/assets"),
  emptyOutDir: false,
  lib: {
    entry: resolve(import.meta.dirname, "src/index.ts"),
    formats: ["es"],
    fileName: "widgets",
  },
}

emptyOutDir: false matters here. Without it, Vite would wipe the rest of pages/assets/: your CSS, images and fonts.

So the order is simple. Build the widgets into pages/ first, then copy pages/ to dist/.

2. Run the Widget Build Before the Site Build

Chain the two in the deploy scripts. npm --prefix runs a script in another folder without a cd: 

"build:DEV1": "npm --prefix widget-library run build -- --mode DEV1 && node scripts/build.mjs dev",
"build:PROD": "npm --prefix widget-library run build -- --mode PROD && node scripts/build.mjs prod"

&& means the site build only runs if the widgets compiled. A type error stops the deploy before anything reaches the bucket.

“Why not add a separate build:widgets script and call that?”

You can, until you need to pass it an argument. In npm run build:widgets -- --mode DEV1, the --mode DEV1 is added to the end of the inner npm --prefix widget-library run build command. There it has no -- in front of it, so npm reads --mode as one of its own options and Vite never sees it. Calling the library's build directly with a single -- avoids that.

Only the deploy scripts get the widget step. The everyday build:dev and build:prod scripts stay fast and copy pages/ as before.

3. Install the Widget Dependencies in CI

This step is easy to miss. CI starts every build from a fresh clone, and widget-library/node_modules is gitignored. On your machine the build works because you ran npm install once. In CI it fails: 

tsc: not found

Add the install to the CI install phase:

# buildspec.yml
phases:
  install:
    commands:
      - node -v
      - npm ci --prefix widget-library
“Why npm ci and not npm install?”

npm ci installs exactly what the lock file lists, and it fails if the lock file and package.json disagree. That's what you want in CI: the same versions every time, or a loud error.

“Won't installing at the repo root cover the subfolder?”

No. npm only installs the dependencies of the package.json you point it at. A nested project needs its own install. (npm workspaces would change that, but you don't need them for one subfolder.)

4. Give the Widgets a Per-Environment Config

The widgets need an API endpoint and key, and dev and prod differ. A common pattern in Vite apps is a table of values, keyed by environment: 

// widget-library/src/lib/config.ts
const variables = {
  DEV1: {
    apiPublicKey: "dev-public-key",
    graphqlApiPublic: "https://dev.example.com/graphql",
  },
  PROD: {
    apiPublicKey: "prod-public-key",
    graphqlApiPublic: "https://api.example.com/graphql",
  },
};

const env: keyof typeof variables =
  import.meta.env.MODE in variables
    ? (import.meta.env.MODE as keyof typeof variables)
    : "DEV1";

export const config = variables[env];

The environment comes from Vite's mode. vite build --mode PROD sets import.meta.env.MODE to "PROD", and Vite replaces it with that string at build time. The dev server runs in mode "development", which isn't in the table, so it falls back to DEV1.

“Why not set VITE_APP_ENV=PROD in the script, like other apps do?”

VITE_APP_ENV=PROD vite build is shell syntax. It works in CI on Linux, but npm on Windows runs scripts in cmd.exe, where it fails. --mode is a plain argument, so it works everywhere, without adding a package like cross-env.

Only public values belong here

Whatever this file holds ends up in widgets.js, and every visitor downloads widgets.js. Minifying the file doesn't hide anything, and neither does reading the value from an environment variable at build time: Vite writes the value into the bundle either way.

So put only keys that are meant to be public here, such as a key for a public, rate-limited endpoint. If your other apps also have a private key or an admin endpoint, leave them out. Anything that has to stay secret belongs on a server, not in a script tag.

“I added the config, but the key isn't in the bundle. Is the build broken?”

No. Vite drops code nothing uses. Until a widget imports config, the values never reach widgets.js. Once one does, they're replaced at build time with the values for that mode.

How to Check the Dev Build Passes

From the repo root:

# 1. install the widget dependencies the way CI does
npm ci --prefix widget-library

# 2. run the dev deploy build
npm run build:DEV1

It passed if the command exits with code 0 and you see, in order:

  • tsc -b && vite build --mode DEV1, with no type errors after it
  • building client environment for DEV1..., which shows the mode reached Vite
  • a line for ../pages/assets/widgets.js with its size
  • the site build's own success line

Then check the output:

  • dist/assets/widgets.js exists.
  • The dev-only outputs look right, for example robots.txt blocks crawlers and there's no sitemap.
  • git status shows pages/assets/widgets.js unchanged. If it's modified, the committed copy was out of date with the widget source, so commit the new one.
  • Once a widget uses the config, search the bundle for the dev key. It should be there after build:DEV1 and absent after build:PROD.

To be fully sure CI will pass, run the same two commands in a fresh clone of your branch. CI only sees what you committed.

Summary

  • Build the widgets into pages/ first, then copy pages/ to dist/. Chain them with &&.
  • Use npm --prefix <folder> run build -- --mode X. A wrapper script loses the --mode flag.
  • Set emptyOutDir: false when Vite writes into a folder it doesn't own.
  • Add npm ci --prefix <folder> to CI. A fresh clone has no node_modules.
  • Choose config values with Vite's --mode. It works on every OS.
  • Everything in the bundle is public. Keep private keys out of it.
